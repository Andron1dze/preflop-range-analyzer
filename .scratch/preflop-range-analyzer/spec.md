# Spec: ML-анализатор префлоп-диапазонов (MTT 8-max, 40bb)

Status: ready-for-human

Итог grilling-сессии (Q1–Q11). Каждый раздел фиксирует принятое решение и его причину.

## 1. Цель и границы

Находить **систематические префлоп-утечки героя** относительно GTO-чартов и показывать их в форме, понятной игроку («оверфолд против 3-бета без позиции при стеке < 30bb»).

**В MVP:**
- турниры MTT, 8-max, эффективный стек около 40bb;
- источники раздач: текстовые HH PokerStars и ручной ввод (для живых турниров);
- анализ только решений героя;
- готовые GTO-чарты (ChipEV), только частоты.

**Не входит в MVP, но схема готова:** модель оппонентов (поле `actor`), потеря EV (`ev_loss`), ICM-чарты (`chart_set.model`), бустинг + SHAP, ветка «пуш или мелкий рейз» в дереве действий.

## 2. Стек

## 3. Архитектура модулей

```
core/                    # без зависимости от веба
  adapters/              # HH → единая модель раздачи
    pokerstars.py
    manual.py
  model/                 # внутренняя модель раздачи (по образцу PHH)
  normalize/             # bb, доли пота, эффективный стек с анте
  charts/                # канонический формат чартов, импортеры, валидация
    importers/pio_range.py
  mapping/               # точная линия → узел + расстояние (Вариант 3)
  stats/                 # Пуассон–Бернулли, z-score, BH-поправка
  models/                # логистическая регрессия со смещением по дереву действий
cli/                     # import, remap, analyze
web/                     # FastAPI, шаблоны, HTMX-фрагменты
charts/                  # канонические файлы чартов (в git)
config/                  # пороги, дерево действий, сетка узлов, профиль героя
```

Принципы:
- `core` ничего не знает о вебе и CLI.
- Анализ — **пакетная задача**: результаты пишутся в БД вместе с версиями, а UI только читает готовое. Любой отчёт воспроизводим.

## 4. Импорт раздач (Q3)

- Слой адаптеров приводит раздачи к **единой внутренней модели раздачи** (структура по образцу PHH).
  - MVP: адаптер PokerStars (текст).
  - Второй адаптер: ручной ввод через веб-редактор.
- **Сырой текст HH хранится всегда.** Это позволяет перепарсить раздачи при изменении логики. У ручного ввода «сырьём» считается сериализованная форма ввода.
- Нормализация выполняется при импорте, результаты сохраняются и могут быть пересчитаны из сырья:
  - сайзинги в bb и в долях пота;
  - эффективный стек в bb с учётом анте.
- Герой задаётся через `hero_name`: параметр импорта или поле профиля в конфиге.

## 5. Модель спота и маппинг (Q4)

Описание спота двухуровневое:

1. **`decisions`** — точная линия в нормализованных числах.
2. **`decision_node_map`** — абстрактный узел, к которому привязано решение.
   - Ключ узла содержит типы действий и позиции, например `40bb|CO:open|HERO=BTN`.
   - Бакеты сайзинга и эффективного стека — отдельные поля узла, в ключ не входят.
   - **Расстояние до узла** — насколько отличаются реальные сайзинг и стек от узловых.
   - Привязка версионируется: `mapping_version` (версия сетки узлов). При смене сетки пересчитывается только маппинг, парсинг не повторяется.

Расстояние используется двумя способами: отбрасывание сильных отклонений по порогу и вес наблюдения `wᵢ` в статистике и регрессии.

## 6. Стадия турнира и ICM (Q9)

- В `decisions` хранятся поля `stage` (`early` / `mid` / `bubble` / `itm` / `ft`, может быть пустым) и `stage_source` (`proxy` / `summary` / `manual`).
- Как определяется стадия:
  - **PokerStars:** приближение по уровню блайндов и среднему стеку (`proxy`). Если есть Tournament Summary, используем его.
  - **Ручной ввод:** стадия обязательна.
- Основной отчёт по утечкам строится на ChipEV-стадиях. ICM-раздачи выводятся отдельным разделом.
- Раздачи с неизвестной стадией в анализ включаются, но по каждому узлу показывается их доля.
- В регрессии стадия — признак. **Ограничение интерпретации:** β по стадии смешивает правильное ICM-сужение с реальными утечками. В UI оно подаётся как «наблюдаемое сужение, частично ожидаемое из-за ICM», а не как поправка. Разделить их можно только с ICM-чартами.

## 7. GTO-чарты (Q11)

- **Канонический формат** (JSON/YAML, хранится в git, каталог `charts/`):

  ```yaml
  chart_set:
    model: chipev
    ante: {type: bb, size_bb: 1.0}   # type: none | each | bb
    source: <источник>
    version: "1"
  nodes:
    - key: "40bb|CO:open|HERO=BTN"
      stack_bb: 40
      sizings: {CO: 2.2, BTN: 7.0}   # bb, включая рейз самого героя
      strategy:
        AKs: {call: 0.35, raise: 0.65}
        # ... все 169 классов рук
  ```

- Один файл — один набор чартов (`chart_set`) со списком узлов.
- Частоты хранятся на уровне **169 классов рук**. Отсутствующее у руки действие означает частоту 0.
- Действия: `fold`, `check`, `call`, `raise`, `allin`.
- `chart_set.model`: `chipev` или `icm:<профиль>`. ICM-чарты подключаются позже без миграции.
- **Анте задаётся типом и размером** (`{type, size_bb}`), а не одной строкой: без размера маппинг не отличит анте 1bb от большого блайнда от анте 0.125bb с каждого игрока. При `type: none` размер равен 0.
- Валидация при импорте (все ошибки выдаются разом):
  - сумма частот по каждой руке равна 1 ± ε, по умолчанию ε = 0.005. Сумма в пределах допуска перенормируется ровно к 1;
  - покрыты все 169 классов, неизвестных классов нет, частоты в [0, 1];
  - `sizings` обязательны и непусты. Если в стратегии есть `raise`, обязателен сайзинг позиции героя (из `HERO=` в ключе);
  - структура анте указана полностью;
  - узлы не повторяются (ключ + стек + сайзинги).
- Синтетические чарты (`source: synthetic-test`) загружаются с пометкой `eligible_for_analysis = false` и в пользовательский анализ не попадают.
- Первый внешний импортер: строки диапазонов Pio/GTO+ (`AA,AKs:0.5,...`).
- `chart_set.version` входит в версию анализа.

**Начальные чарты MVP** (RFI с UTG и BTN, защита BB против открытия с BTN, 40bb) — см. открытый вопрос 1 в §13.

## 8. Статистический движок (Q5, Q6)

- Ядро сравнения не привязано к игроку: в `decisions` есть поле `actor` (`hero` или id оппонента). В MVP анализируется только `actor = hero`.
- Для каждого решения `pᵢ` — GTO-частота выбранного действия для **реально пришедшей руки**.
- **Верхний уровень (узел).** Ожидание против факта по распределению Пуассона–Бернулли:
  - ожидаемое число действий: `E = Σ wᵢ·pᵢ`;
  - дисперсия: `Var = Σ wᵢ²·pᵢ(1−pᵢ)`;
  - `z = (факт − E) / √Var`.
- Узел помечается как утечка, если `|z| > z_threshold` и выполнен порог `min_sample`.
- **Детализация помеченного узла** по двум осям:
  - зоны GTO-частоты: «чистое действие» (p > 0.9), «микс» (0.1–0.9), «никогда» (p < 0.1). Отклонения в «миксе» по умолчанию считаются шумом;
  - группы рук: пары, одномастные бродвеи, одномастные коннекторы, разномастные бродвеи и т.д.
- Поправка Benjamini–Hochberg выводится **отдельной колонкой**, а не фильтром. Отчёт сортируется по z-score.
- Пороги `z_threshold`, `min_sample`, границы зон и порог расстояния задаются в конфиге, а не константами в коде.
- Поле `ev_loss` (может быть пустым) есть в схеме с самого начала.

## 9. ML-слой (Q7, Q8)

Второй слой поверх статистического движка ищет паттерны отклонений **между узлами**.

- **Модель:** логистическая регрессия, в которой GTO-частота входит фиксированным смещением:
  `logit P(действие) = logit(pᵢ) + β·x`.
  Коэффициенты β напрямую читаются как систематические отклонения от GTO.
- **Признаки x:** позиция, бакет стека, бакет сайзинга, тип линии, группа руки, зона частоты, стадия.
- Веса наблюдений `wᵢ` берутся из расстояния до узла. Регуляризация L2.
- **Декомпозиция по дереву действий** (задаётся в конфиге, не в коде):
  1. Продолжить или сбросить: смещение `logit(1 − p_fold)`.
  2. Агрессия или колл при условии продолжения: смещение `logit(p_raise / (1 − p_fold))`.
  3. *(позже)* Пуш или мелкий рейз внутри агрессии.
- Технические детали:
  - частоты обрезаются до `[ε, 1−ε]`;
  - решения с неопределённой условной вероятностью (`p_fold ≈ 1`) исключаются из шага 2;
  - в спотах для открытия (RFI) шаг 2 вырождается.
- **Реализации:**
  - эталон — `statsmodels.GLM(family=Binomial(), offset=..., var_weights=...)`, даёт стандартные ошибки и доверительные интервалы для β;
  - собственная реализация на numpy (IRLS + L2) сверяется с эталоном в тестах.
  - `sklearn.LogisticRegression` не используется: он не поддерживает смещение.
- Интерфейс показывает β с доверительными интервалами и текстовой интерпретацией.

## 11. Веб-интерфейс и API (Q10)

- Загрузка HH-файлов. Импорт запускает фоновую задачу.
- **Редактор ручного ввода:** позиции, стеки, анте, действия с сайзингами, карты героя, стадия (обязательна).
- Запуск анализа (фоновая задача) и список прогонов `analysis_runs`.
- Отчёт по утечкам:
  - таблица узлов (z, n, BH-q, доля неизвестной стадии);
  - раскрытие узла по зонам и группам рук;
  - **сетка 13×13** с подсветкой отклонений.
- Раздел ICM-стадий.
- Панель β-коэффициентов с доверительными интервалами и текстовыми выводами.

CLI: `import`, `remap`, `analyze`.

## 12. Тестирование

- pytest, разработка через TDD.
- **Адаптеры:** эталонные фрагменты HH PokerStars (открытие, 3-бет, пуш, лимп, сайд-поты, анте) → ожидаемая внутренняя модель.
- **Нормализация:** точные значения bb, долей пота и эффективного стека с анте.
- **Маппинг:** golden-файлы (точная линия → узел + расстояние) по каждой версии сетки.
- **Чарты:** валидация (сумма частот, покрытие 169 классов) и парсер строк Pio.
- **Статистика:** z-score на синтетических данных с известным ответом.
- **Регрессия:** на синтетических данных с заданными β реализация на numpy совпадает со statsmodels в пределах допуска.

## 13. Открытые вопросы

1. **Источник начальных чартов.** Чарты для узлов MVP нужно взять из реального источника (солвер, GTO Wizard, бесплатные чарты с указанной лицензией) и записать его в `chart_set.source`. Придумывать частоты нельзя: анализ будет мерить отклонения от выдуманной стратегии. Для **тестов** допустимы синтетические чарты с явной пометкой `source: synthetic-test`, которые не попадают в пользовательский анализ.
2. Сетка узлов для Варианта 3 (бакеты стека и сайзинга, метрика расстояния, порог отсечения) уточняется после выбора чартов: она определяется тем, какие узлы чарты реально покрывают.
3. Правила приближения стадии по уровню блайндов (`proxy`) для MTT на PokerStars.
